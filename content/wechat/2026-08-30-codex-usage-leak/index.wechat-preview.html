Tibo 赛博回血：不是庆祝，是 Harness 大修回执

这次 Reset 不是庆祝用户数创新高，而是 Codex Harness 大修完成后的用量回馈。

8 月 30 日，Tibo 又一次给 Codex 用户“赛博回血”。

Codex 刚刚迎来用户数创新高。看到 Tibo 再次宣布全量 Reset，很多人的第一反应自然是：这又是一轮庆祝里程碑的用户福利。

但 Tibo 对这次 Reset 给出的解释，并不是庆祝。

他说，Codex 工程团队连续处理了数千份报告，找出并修复了一批长期存在的异常消耗。根据使用方式不同，同一份 Codex 用量现在预计可以多支撑 10%～50%。随后，所有 Codex 和 ChatGPT Work 付费用户的用量被重置。

所以，这次“赛博回血”更像一张工程回执：前台是用量条重新回满，后台则是 Codex Harness 对上下文、Memory、长程任务、多 Agent 和工具协议做了一轮系统性大修。

听上去像是 OpenAI 把水箱换大了。看完 Tibo 列出的八项修复，才会发现事情更像是：水箱还是那个水箱，过去有几根管道一直在悄悄漏水。现在，工程团队终于拿着扳手把它们找了出来。

这八个漏水口包括：Compaction、Memory、Goals、Automations、Subagents、Computer History、rolling summaries 和 MCP。

名字看上去很散，放到一张 Agent runtime 图里就不散了。

在继续之前，先交代这篇文章怎么判断“OpenAI 到底做了什么”。

第一层证据是 Tibo 的帖子。八项问题和所有影响数字都来自这里。第二层是 OpenAI 官方文档，它解释 compaction 这类能力的公开工作方式。第三层是 Codex 开源仓库：在帖子前后的提交里，可以直接看到图片预算、Memory Stop scope、Goal 熔断、service tier 继承和 MCP typed content。第四层是 GitHub issue 与社区报告，它们能还原用户遇到的症状，却不能代替生产统计。

这四层不会被混在一起。源码能对上的，我会说“能看到”；只有协议、没有 scheduler 的，我会明确说“看不到”；从工程经验得出的判断，也不会包装成 OpenAI 官方结论。

一个请求背后，藏着一座后台小工厂

我们习惯了聊天产品的节奏：问一句，答一句。于是很容易认为，额度下降就是模型正在回答问题。

Agent 不是这样工作的。

你只说了一句“帮我修复登录 Bug”，它可能会读项目规则、搜 memory、制定计划、运行命令、读取日志、继续推理。上下文变长以后，它还会压缩历史；任务复杂时，它会叫来子 Agent；会话离开前台以后，产品可能生成标题、短摘要或历史笔记；Goal 模式甚至会在当前一轮结束后主动续跑。

用户只看见左上角的请求。真正消耗用量的，是整座工厂。

这也是这次事件最值得研究的地方。它不是某个模型突然“变费了”，而是一组 runtime 边界同时出了小问题：有的内容被重复带入上下文，有的 worker 到点不下班，有的子任务越过了根任务的成本选择，还有的工具结果被包装了两次。

单个问题可能只多消耗一点。乘上几百轮、几万名用户和一棵子 Agent 树，就会变成一条肉眼可见的额度曲线。

漏水口一：压缩历史时，旧图片没有真正变轻

长会话迟早会碰到 context window。Codex 会把早期对话压成更短的内容，再保留最近几轮原始历史，这个过程叫 compaction。

问题在于，最近几轮不一定只有文字，还可能有截图。

旧实现有时会压缩文字，却把旧图片继续留在 replacement history。账面上历史短了，真正送给模型的上下文仍然很重。下一轮发现又快满了，于是再次触发 compaction。

这像搬家时扔掉了一叠旧报纸，却把最占地方的衣柜原样搬进新房，然后惊讶地发现新房又满了。

Codex 当前开源源码里，可以看到直接对应的修复：图片会先估算大小，再换算成 retained-message budget；图片和它前后的 harness 标签要么一起保留，要么一起舍弃。

更有意思的是，如果最新边界里的图片装不下，runtime 不会为了“别浪费剩余空间”又捡回更旧的便宜文本。因为 compaction 需要保住连续的执行前沿，不是尽可能塞满一个背包。

Tibo 说，修复后经常使用图片的用户，用量下降约 10%。这个数字来自 OpenAI 的生产统计，不是开源单元测试能证明的统一比例。

漏水口二：Memory worker 一直问“我能下班了吗”

Codex 的 memory 会在后台整理历史，把零散会话变成以后可复用的记忆。为此，runtime 会启动一个内部 consolidation agent。

问题是，这个后台 worker 有时继承了前台任务的 Stop hooks。

Stop hook 本来是一套很实用的机制。模型说自己做完以后，先问外部检查器：“我现在真的能停吗？”项目可以要求测试必须通过，用户可以要求某个产物必须存在。如果检查失败，Agent 会继续一轮。

但 memory worker 的工作只是整理记忆。它如果被要求证明整个项目任务已经完成，就可能永远给不出正确答案。Tibo 提到一个极端 thread，检查自己能不能停止多达 15000 次。

修复不是关闭所有安全检查，而是给 memory consolidation 单独定义 Stop scope：

  • 用户和项目级的完成检查、插件 hook、用户通知被排除；
  • 系统与组织的 managed policy 继续有效；
  • executor cleanup 始终执行。

这条修复背后有个很重要的工程判断：后台任务可以复用 Agent loop，但不能把前台 session 的身份、hook、通知和终止条件整包复制过去。

它应该继承安全政策，不应该继承所有生活习惯。

漏水口三：Goal 完成了，runtime 还在继续

普通聊天有天然终点：模型回答完，就等下一条用户消息。

Goal 模式不一样。一个持久目标可以在当前 turn 结束后继续推进，直到完成、被阻塞、达到用量限制或用户停止。

这时，“模型觉得做完了”和“runtime 进入终态”必须是两件不同的事。

如果目标已经完成，状态仍然是 Active，continuation 会再跑一轮。如果执行宿主坏了，模型不断重试同一个命令，却没有熔断器，用量会沿着一条没有进展的路径继续累积。Tibo 说他们见过单个例子消耗每周额度的 15%～70%。

当前源码加入了一条很具体的保险丝：

  • 任意成功工具调用会把失败计数清零；
  • 只有默认 exec 确实进入 handler 后失败，才记为执行失败；
  • 相同 Goal 连续三轮没有成功工具、同时发生执行失败，Goal 会变成 Blocked: execution unavailable。

为什么不是失败一次就停？因为一次错误可能只是临时故障。为什么不能一直重试？因为“下一次也许会好”不能成为无限循环的运行政策。

三轮未必是所有 Agent 的最优值，但 bounded retry 和 no-progress detection 是所有长程 Agent 都应该有的能力。

漏水口四：Automation 跑得比日历勤快

Tibo 说，某些自定义 schedule 实际执行频率高于用户配置。

这项修复目前不能从 Codex 开源仓库里完整还原。仓库公开了 Hourly、Daily、Weekdays、Weekly 等 schedule schema，也能识别 automation thread，但真正决定“下一次几点运行”的产品 scheduler 不在这里。

因此，我们不能假装知道问题究竟来自时区、recurrence 展开、设备恢复，还是重复投递。

能确定的原则是：计划任务不能靠 prompt 保证频率。scheduler 必须持久保存 last-fired watermark、dedup key、lease 和幂等状态。否则“每天一次”遇到重启、恢复或多实例并发，就可能变成“一次没少，偶尔多送几次”。

漏水口五：子 Agent 私自坐上了更贵的车

Tibo 披露了两个子 Agent 问题：Luna 等小模型有时会在用户没有明确要求时选择更强的 helper；根模型没有使用 /fast，却可能让子 Agent 跑 /fast。

开源代码能直接看到第二项修复：service tier 现在由 root thread 持有，并传播到整棵 Agent tree。

子任务仍然可以选择合适的 model 和 reasoning effort，因为那属于能力匹配；但 default 还是 Fast/Priority 属于用户在根任务上做出的成本与延迟选择，子 Agent 不能私自升级。

同时，子 Agent 的 token usage 会计入 root Goal。否则父任务看起来预算健康，真正昂贵的工作全被委派给子进程，和一家公司只统计总部电费、不统计所有分厂差不多。

漏水口六、七：历史和摘要，总在偷偷多做一遍

Computer History 会把用户近期在应用和网页里的活动带入上下文。它很有用，也天然容易重叠：10:00～10:10 和 10:05～10:15 的两个窗口，共享一半内容。

Tibo 说旧实现会反复总结重叠 activity，某些个案一周消耗接近总用量的五分之一。

当前开源仓库没有 Computer History 的采集 cursor、窗口去重或摘要算法，所以不能声称 OpenAI 最后用了 event ID、内容 hash 还是时间水位线。Agent 工程师能学到的是：增量系统如果没有稳定的 processed frontier，就会把滑动窗口误当作全新数据。

rolling task summaries 是另一种善意的后台工作。它本来想给任务生成短摘要，却错误地在普通 turns 后触发额外请求，累计约增加 1% token。Tibo 说旧功能已经被禁用。

Codex 当前源码另有一套 TUI recap，它不一定是同一功能，却展示了更健康的触发方式：至少三个 completed turns、距离上次至少两轮、线程失焦三分钟、只取近期历史、一次只跑一个请求，并在写回前检查 thread revision。

这类后台功能最怕“顺手”。普通 turn 结束以后顺手再调一次模型，代码很短，账单很长。

漏水口八：MCP 工具结果被包装了两次

MCP 工具结果不是普通字符串。它可以包含 text、image、audio、resource 和 structured content。

最省代码的做法，是把整个 content array 序列化成一段 JSON 文本，再塞进 function-call output。问题是，普通文本本来已经是文本，又多了一层字段名、引号和转义；图片和音频原本有明确类型，也被压扁成需要重新解释的字符串。

当前源码把这些内容转换为 typed items：Text、Image、Audio、Encrypted 分别保留自己的类型；只有真正存在的 structured content 才序列化一次。每个 MCP 工具还可以设置独立 output token limit，Code Mode 保留 raw result，模型历史只接收预算内的投影。

这个设计可以概括成一句话：日志、程序、UI 和模型上下文需要的不是同一种表示。

把同一份大字符串广播给所有消费者，看起来通用，最后通常只是把成本和复杂度推迟到下游。

这四类问题在任何 Agent 产品里都可能出现。模型越能长时间自主工作，泄漏的乘数越大。

真正值得带走的六条工程原则

第一，每一枚 token 都要有 owner。至少能归因到 user action、turn、Goal、background feature 和 agent lineage。

第二，每个后台 worker 都要有独立 lifecycle。可以复用 Agent loop，但要单独定义权限、hook、通知、重试和终态。

第三，所有 retry 都必须有预算和进展判定。不能只问“这次失败了吗”，还要问“连续几轮没有产生有效进展”。

第四，层级系统的成本政策由根节点拥有。子 Agent 可以选能力，不能越过 root 的 service tier、预算和并发边界。

第五，一种事实只保留一个 canonical representation。工具原始结果、日志、UI 和模型上下文分别投影，不要反复字符串化。

第六，后台成本必须进入可观测性。不能只看平均 token/turn，还要看 background request count、fan-out ratio、Goal continuation、compaction 间隔和 p95/p99 长尾。

10%～50%，你会落在哪一边

这不是统一扩容，更不是所有用户固定增加 50%。

如果你主要做短文本任务，很少用图片、Goal、Automation、Computer History 和多 Agent，改善可能更接近区间低端。

如果你经常贴截图、做 UI 或 Computer Use，让任务经历多次 compaction，retained-image 修复会更明显。

如果你重度使用 Goal、长期自主运行、经常 spawn 子 Agent，或者曾遇到执行宿主故障，一次被熔断的失控循环就可能省下很大一段用量。

MCP 工具多、返回内容复杂的工作流，也会从 typed content 和工具级预算中受益。

真正影响结果的还有模型、任务长度、缓存命中、工具调用、产品表面和部署进度。因此，这些只能算场景判断，不是效果承诺。

更值得期待的是，Tibo 说 OpenAI 正在做应用内用量归因，让用户直接看到额度去了哪里。

只显示“本周还剩 37%”是不够的。用户还应该知道，多少花在前台任务，多少花在 compaction、子 Agent、memory 和 automation。透明的 attribution 不只是客服功能，它会迫使 runtime 为每一类后台工作找到 owner。

对普通用户来说，这也提供了一套更可靠的观察方法。不要只比较“今天用了几个小时”，还要比较任务形态：是不是同一个长 thread、有没有大量截图、发生了几次 compaction、是否开启 Goal、spawn 了多少子 Agent、是否在使用 Computer History 或 Automation。同样工作半小时，一个新建的短任务和一个经历十轮压缩、带着多张图片的长任务，本来就不是同一份计算负载。

如果修复生效，最先出现的变化未必是某次回答特别省，而是长任务不再出现异常陡降：图片压缩后真正变轻，坏掉的执行环境能让 Goal 停下来，子 Agent 不再擅自切换成本档位，后台摘要也不再跟着每个普通 turn 追加一笔。

结语

这次 Codex 更新最有意思的地方，是它没有要求模型突然变得更聪明，却可能让同一份订阅多完成 10%～50% 的工作。

省下来的不是凭空创造的算力，而是原本不该发生的调用：不该留下的旧图片、不该继承的 Stop hook、不该继续的 Goal、不该升级的子 Agent、不该重复的摘要和编码。

传统后端系统早就把线程泄漏、重试风暴、重复投递和资源记账错误视为 correctness bug。Agent runtime 只是把同一类问题换成了 context、tool call、background model request 和 token budget。

模型能力决定 Agent 能走多远；runtime 的边界决定它会不会在路上把油漏光。
