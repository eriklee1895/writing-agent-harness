# 微信双栏图片上传：光标插图会拆开列容器

## 已验证现象

2026-09-29，星舰文章的本地双栏预览正常，使用现有 publisher 在微信 ProseMirror 编辑器逐个替换图片占位符时：

- 六张图片中的第2、4张报告上传超时，都是双栏右侧图片。
- 保存后实际只有四个正文图片节点；前两个节点虽有 CDN 地址，实际显示宽高均为0。
- 微信将图片作为独立 block 节点插到双栏的 flex 父级，原本49.5%宽的子列被拆成多个兄弟 section，图片节点在多个固定宽度子项之间被挤到0宽。
- 下一张上传还会替换之前的图片，因此「图片数量未增加」不一定是网络上传失败。

## 本次修复

在同一篇已保存草稿内操作，保留本地 canonical source：

1. 将图片放入独立的顶层占位段落中，串行上传。
2. 等待六张图片都取得微信 CDN 地址，保存每张对应的元数据。
3. 把这些 CDN 图片标签代回已审阅的完整双栏 HTML，一次性插入正文；不再在列内用光标逐图插入。
4. 检查图片实际 bounding box 和配对关系，而不只检查节点数。
5. 保存草稿，重新打开，确认六张图均可见、两组各两张同排、封面存在、正文没有外链。

结果：六张图片全部上传成功；保存重新打开后，两组图片每列约286px、左右同排，其余两张全宽图片正常。没有创建重复草稿或点击发表。

## 后续复用

- 当前共享 publisher 尚未改造为自动两阶段上传；这次采用 article-scoped 修复脚本，运行态证据放在 publisher 的 `.artifacts/`，不入 Git。
- 含嵌套双栏图片的文章，应采用「先上传获取 CDN，再整体注入排版」的顺序。
- 上传成功验收必须包括数量、CDN、非零显示尺寸、双栏位置，以及保存重新打开后的状态。
- `image_count` 应反映实际验证数量，不能只把请求数量写成成功数量。

## 表格列宽与再次编辑

- 本文附表最终采用22% / 24% / 54%，保存后重新打开核对9行（表头加8行）均保留比例。
- flex单元格使用百分比width和flex-basis，外层不加横向padding；横向padding放在内层section。微信可能移除box-sizing，内层padding可以避免三列宽度加上padding后超过100%。
- 从编辑器DOM读取HTML后再次整体注入前，要去除无src/data-src的编辑器辅助img及ProseMirror-separator。否则部分辅助节点会被重新解析成没有图片地址的正文图片，造成额外的零宽高节点。实际图片、图注与用户文字需保留。
